# 文档一：架构与方案选型

> GBA 60Hz · Android 原生化移植
> 目标：把现有的"单文件 HTML + WASM 内核"改造成可安装、可上架的 Android App，
> **内核与现有 UI 一行不改**，100% 复用。

---

## 1. 三条技术路线对比

| 路线 | 做法 | UI 复用 | 内核复用 | 工作量 | 风险 | 结论 |
|---|---|---|---|---|---|---|
| **A. WebView 套壳 + 原生桥接**（推荐） | Kotlin 原生壳承载 WebView，加载单文件 HTML，补原生能力桥接 | 100% | 100% | 低（1~2 周） | 低 | ✅ 采用 |
| B. 真原生 Compose UI + 内核编 .so | 用 Jetpack Compose 重写全部界面，Rust 内核编成 ARM .so 经 JNI 调用 | 0%（全部重写） | 需改 ABI 适配 | 高（2~3 月） | 高 | ❌ 与"复用现有 UI"矛盾 |
| C. TWA（Trusted Web Activity） |  PWA 套壳，要求有 https 站点与 Digital Asset Links | 100% | 100% | 极低 | 依赖外站 | ❌ 本作无公网站点，且需网络 |

**为什么选 A**：你的核心资产是 84KB WASM 内核 + 4710 行前端（8 主题 × 10 皮肤 × 8 形态的 CSS 质保真、完整 WebGL 画质、IndexedDB 存档系统、触控/手柄交互）。路线 B 会让这些全部作废重写，与"根据现有代码和 UI 开发"的目标直接冲突。路线 A 只补一层原生能力，是投入产出比最高的选择。

> 关于路线 B 的现实：即便将来要做，也是"把现有 ABI 内核编成 .so + 用 JNI 暴露同一套 C 函数"，前端逻辑仍可大量复用；但 UI 用 Compose 重写等于重做项目。本方案先把 A 做扎实，B 留作未来演进（见 §6）。

## 2. 整体架构

```
┌─────────────────────────────────────────────────────────┐
│                    Android App (Kotlin)                  │
│  ┌───────────────────────────────────────────────────┐  │
│  │ MainActivity                                       │  │
│  │  ├─ WebView (硬件加速, JS/DOM/WebGL 开启)          │  │
│  │  ├─ WebViewAssetLoader (assets → https origin)     │  │
│  │  ├─ WebViewClient (本地资源拦截/外链跳转)          │  │
│  │  └─ WebChromeClient (文件选择/全屏/console)        │  │

│  │ GbaBridge (@JavascriptInterface, 注入名 GbaNative) │  │

│  │  └─ (下载/分享/震动兜底)                           │  │
│  └───────────────────────────────────────────────────┘  │
│                          ↕ JS Bridge                     │
│  ┌───────────────────────────────────────────────────┐  │

│  │  ├─ 全部 UI / CSS 皮肤系统                         │  │

│  │  └─ WASM 内核 (gba_frame 等 ABI)                   │  │
│  └───────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

### 2.1 最关键的一环：origin 与 WebViewAssetLoader

`file://` 协议下，IndexedDB、crypto.subtle、部分 WebGL 特性会被浏览器限制（原项目 `serve.py` 就要求用 http 打开）。Android WebView 同样如此。

解决：用 AndroidX 的 `WebViewAssetLoader` 把 `assets/` 映射到 `https://appassets.androidplatform.net/assets/`，页面从一个"合法的 https origin"加载，于是：

- IndexedDB 正常（ROM / 存档 / 缩略图 / 金手指都能存）
- WebAudio / AudioWorklet 正常
- WebGL 纹理上传正常
- 不受 `file://` 的 CORS 限制

这是整个方案的地基，代码见 `MainActivity.assetLoader` 与 `shouldInterceptRequest`。

### 2.2 模块清单

| 文件 | 职责 |
|---|---|
| `app/build.gradle.kts` | 依赖与 SDK 版本；`androidx.webkit` 提供 AssetLoader |
| `AndroidManifest.xml` | 权限（VIBRATE/INTERNET）、Activity 配置、外部 .gba 打开 |
| `MainActivity.kt` | WebView 配置、资源拦截、SAF 文件选择、全屏、返回键、生命周期 |
| `GbaBridge.kt` | JS→原生：toast / 震动 / 分享 / 保存截图 |
| `assets/GBA-60Hz.html` | 由 `tools/sync_assets.sh` 从 dist 同步的单文件成品 |
| `tools/sync_assets.sh` | 构建产物同步脚本 |
| `res/` | 主题、字符串、自适应图标、备份规则 |

### 2.3 数据流

1. **启动**：`onCreate` → 配置 WebView → `loadUrl(APP_URL)` → AssetLoader 从 assets 返回 HTML。
2. **页面加载完成**：注入 JS 增强（`Js.INJECT`）：接管 blob 下载、外部 ROM 打开、分享降级。
3. **导入 ROM**：用户点页面"载入 ROM" → `<input type=file>` 触发 `onShowFileChooser` → 打开 Android SAF → 选中的 `content://` Uri 回传给 WebView → 页面原有 JS 读取并在 IndexedDB 落库。
4. **运行**：所有游戏逻辑、渲染、音频、存档都在 WebView 内完成，与网页版行为完全一致。
5. **原生增强**：震动/分享/保存截图通过 `GbaNative` 桥接调用原生能力。

## 3. 权限说明（上架隐私合规）

| 权限 | 用途 | 是否必需 |
|---|---|---|
| `android.permission.VIBRATE` | 触屏按键轻震动反馈 | 可选（不用震动可删） |
| `android.permission.INTERNET` | WebViewAssetLoader 本地 origin、错误页 | 必需（无实际外网请求） |

**没有**读取存储、定位、通讯录等敏感权限——所有 ROM/存档都在 App 私有空间与 SAF 授权范围内。这对上架隐私声明非常有利：可在 Play 商店声明"不收集、不共享任何用户数据"。

## 4. 能力与已知边界

| 能力 | WebView 中状态 | 处理 |
|---|---|---|
| 触屏虚拟按键 | ✅ 完全正常 | 无改动 |
| 键盘 / 手柄 | ✅ Gamepad API 由 WebView(Chromium) 支持 | 无改动；手柄即插即用 |
| 震动 | ⚠️ WebView 对 `navigator.vibrate` 支持不一 | `GbaBridge.vibrate` 兜底 |
| `navigator.share` | ⚠️ 多数 WebView 不可用 | 注入脚本降级到原生分享/文本分享 |
| 截图下载 | ⚠️ WebView 下载管理器行为不一 | 注入脚本把 blob 转 dataURL 走原生保存 |
| 全屏 | ⚠️ 需原生配合 | `onShowCustomView` 全屏覆盖层 |
| 文件导入 | ⚠️ `<input file>` 需原生chooser | `onShowFileChooser` + SAF |
| 后台运行 | ⚠️ 切后台应暂停 | `onPause` 注入 autoSave + 页面 visibilitychange 兜底 |
| WebGL 画质 | ✅ 硬件加速下正常 | 低端机可自动降级到 2D（页面原有逻辑） |

## 5. 目标设备与兼容范围

- **minSdk 24**（Android 7.0）：覆盖绝大多数在役设备；WebViewAssetLoader 支持到 21+。
- **targetSdk 35**（Android 15）：满足当前 Play 商店上架要求（需每年提升）。
- **架构**：`arm64-v8a` / `armeabi-v7a`（WASM 在 WebView 中运行，与 CPU 架构无关，但限制架构可减小包体并为未来原生内核留位）。

## 6. 未来演进：从 WebView 到"半原生"

若将来用户量增大、追求极致性能，可平滑演进而不推翻现有资产：

1. **阶段 1（当前）**：WebView 承载全部逻辑。
2. **阶段 2**：把 WASM 内核编成 `.so`，用 JNI 暴露同一套 `gba_*` ABI；前端把 `initCore()` 从 `WebAssembly.instantiate` 改为 `GbaNative.coreCall(...)`。**UI 与业务逻辑完全不动**。
3. **阶段 3（可选）**：逐步用 Compose 替换个别页面皮肤，但保留整体结构。

由于 ABI 是稳定的 C 接口，阶段 2 的改造成本远低于从零重写内核。
